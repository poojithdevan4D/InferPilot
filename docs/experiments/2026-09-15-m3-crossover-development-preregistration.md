# M3 development — workload-rate crossover discovery

**Status:** development protocol frozen before measurement. This is policy-development evidence,
not held-out confirmation.

## Question and hypothesis

Can the same fixed request shape require different SLO-feasible, TPOT-minimizing scheduler widths at
low and high offered load? Existing C7 evidence found width 3 at 4 QPS and width 4 at 6 QPS, but the
4-QPS TPOT margin was only 0.064 ms. M3 deliberately separates the regimes further.

The fixed hypothesis is that 2 QPS selects a narrower scheduler than 6 QPS. At low load, narrow
scheduling should remain under the TTFT ceiling and reduce TPOT; at high load, queueing should make
width 4 necessary. A constant selection, no feasible candidate, or a negligible objective gap is a
valid negative result.

## Fixed matrix

| Item | Value |
|---|---|
| Model/hardware | Qwen2.5-0.5B-Instruct on the existing RTX 3050 environment |
| Rates | 2 and 6 QPS |
| Candidates | `max_num_seqs={1,2,3,4}` |
| Fixed engine fields | `max_num_batched_tokens=512`, chunked prefill explicitly enabled |
| Workload | Poisson, 128 prompt / 32 output tokens, 256 measured + 4 warm-ups |
| Prompt content | fixed `prompt_seed=3001` across every cell |
| Arrival blocks | independent `arrival_seed={60,61,62}` at both rates |
| SLO | TTFT p95 ≤250 ms and TPOT p95 ≤8.5 ms in every block |
| Objective | minimum mean block-level TPOT p95 among robust-feasible candidates |
| Repetitions | one run per cell (`min_runs=1`) |
| Total | 24 cells |

The exact configs and study contracts are generated by
`experiments/m3-crossover-development/generate_configs.py`. Its `--check` mode is read-only and
fails on any missing, extra, or byte-changed JSON.

## Execution, acceptance, and stopping

Execution order is seed 60→61→62; within each seed, width 1→2→3→4; within each width, rate 2 then
rate 6. This interleaves regimes while preserving a deterministic resume order.

A cell is accepted only when COMPLETED, baseline-eligible, effective configuration verified,
telemetry complete, lifecycle and phase evidence complete, 256/256 requests successful, arrival
provenance correct, and dispatch-drift p95 ≤10 ms. One identical retry (two attempts maximum) is
allowed only when the sole failed gate is `dispatch_drift_exceeded`; all attempts are preserved. No
seed substitution or config change is allowed. Any other rejection, or a second drift rejection,
stops the study without using performance outcomes to change the design.

Only after all 24 cells are accepted may the two blocked reports be opened and compared. This study
locates a potential policy crossover; it does not establish significance, production SLOs,
deployment safety, model/GPU generality, or switching benefit.
